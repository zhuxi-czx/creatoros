# 版本迭代与发布流程

适用于 CreatorOS（小程序 + 后端 + 后台 + H5 多端）的轻量发布规范。

## 一、版本号规则（SemVer）

`主版本.次版本.修订号`，以**小程序版本**为主线：
- `1.0.1` 修订：bug 修复、文案微调
- `1.1.0` 次版本：新功能（向后兼容）
- `2.0.0` 主版本：不兼容大改

后端 / 后台 / H5 不单独编号，跟随主线；每次小程序发布在 git 打 tag（`v1.0.0`）锚定全仓代码快照。

## 二、🔑 最重要的一条：后端必须向后兼容

小程序发版后，**用户不会立即升级**，线上会同时存在多个小程序版本。而后端是「一直在线、随时部署」的，所以：

- 后端 API 改动**只增不删改**：加字段 / 加接口 OK；删字段 / 改字段含义 / 改返回结构会**直接弄坏老版本小程序**
- 必须做破坏性改动时：新开一个接口（或加版本前缀），等旧版小程序自然淘汰后再下线旧接口
- 后台（admin）/ H5 是即时全量更新、无碎片，可以随意改

> 一句话：**改后端前先想"线上最老的那版小程序还能用吗"。**

## 三、日常迭代流程

1. 在 `main` 上开发（小改）或开 `feat/xxx` 分支（大功能），完成后合回 `main`
2. 每个改动一个语义化 commit；功能完成 `npx tsc --noEmit` + 构建自测
3. 部署（无审核的部分可随时上）：
   - 后端：`rsync server/src` → `npm run build` → `pm2 restart`（schema 变更先 `prisma db push`）
   - 后台 / H5：本地 build → `rsync dist`
4. 攒够一批面向用户的改动 → 准备发小程序版本

## 四、发小程序版本

1. 更新 `CHANGELOG.md`（新增一节，写用户可见的改动）
2. 决定版本号（修订/次/主），在微信开发者工具填该版本号上传
3. 打 tag 锚定代码：
   ```bash
   git tag -a v1.1.0 -m "1.1.0: 简述"
   git push origin v1.1.0
   ```
4. 微信后台「提交审核」→ 通过后「发布」
5. **审核期间不要再改线上后端的破坏性逻辑**（审核用的是当时的代码 + 线上后端）

## 五、回滚预案

- **后端 / 后台 / H5**：`git checkout <上个稳定 tag>` → rebuild → 重新 rsync/restart
- **小程序**：微信后台支持「版本回退」到上一个已发布版本（数分钟生效）
- 数据库：每天 2:00 自动备份（保留 7 天），误操作可恢复

## 六、发布节奏建议

- 小程序审核有周期（数小时～1 天），**别为单个小修单独发**——攒一批一起发
- 紧急线上 bug：能在后端/后台修的优先在那修（即时生效，不用等审核）；只有必须改小程序端的才走审核
- 每次发布对着 `docs/验证清单.md` 真机过核心链路
